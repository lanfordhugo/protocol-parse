# Diff Review

## Overview

系统化的代码审查流程，用于发现代码变更中的潜在问题和改进点。重点关注正确性、安全性和代码质量。

## 审查原则

### 审查范围

1. **逻辑错误和错误行为** - 算法错误、条件判断错误、状态管理错误
2. **边界条件** - 空值、空集合、极值、并发场景未处理
3. **空值/未定义引用** - 缺失空值检查、未初始化变量、可选值未处理
4. **竞态条件和并发问题** - 数据竞争、死锁、共享状态保护缺失
5. **安全漏洞** - 注入攻击、权限检查缺失、敏感数据泄露
6. **资源管理或泄漏** - 文件/连接未关闭、内存泄漏、资源未释放
7. **API 合约违规** - 接口误用、参数校验缺失、返回值处理错误
8. **缓存问题**
   - 缓存失效问题 - 更新数据但缓存未失效
   - 缓存键相关错误 - 键计算错误、冲突、缺失必要参数
   - 无效缓存 - 缓存了错误结果、缓存条件错误
   - 缓存无效 - 完全未命中缓存、重复计算
9. **违反现有代码模式或约定** - 架构不一致、命名规范违反、设计模式误用

### 重要规则

**必须遵守：**

1. **不要报告推测或低置信度问题** - 所有结论必须基于对代码库的完整理解
2. **并行探索提高效率** - 调用多个工具并行探索代码库，不要花太多时间探索
3. **同时报告已有 Bug** - 如果发现代码中的现有 Bug，也应报告，这对维护代码质量很重要
4. **注意 Git 状态** - 如果给定特定 git commit，可能未检出，本地代码状态可能不同

## 审查流程

### 第一步：理解变更上下文

**目标：** 了解变更的目的、范围和影响

**必须执行的 Git 操作：**

```bash
# 查看变更摘要
git diff --stat <commit>

# 查看完整 diff
git diff <commit>

# 查看提交信息
git log -1 --format=fuller <commit>
```

**并行获取上下文：**

1. 读取修改的文件，理解变更内容
2. 搜索相关模块和依赖
3. 查看相关的测试文件

**重要：** 必须先执行上述 Git 命令获取 diff，不要跳过此步骤！

### 第二步：分类审查

**按文件类型/模块分类：**

- 核心业务逻辑
- 数据访问/持久化
- API/接口层
- 配置/基础设施
- 测试代码

### 第三步：逐项检查

**使用以下检查清单：**

#### 1. 逻辑正确性

- [ ] 算法实现是否正确？
- [ ] 条件判断是否完整？
- [ ] 状态转换是否合理？
- [ ] 异常处理是否恰当？

#### 2. 边界条件

- [ ] 空值/None 是否处理？
- [ ] 空集合/空字符串是否处理？
- [ ] 数值极值是否处理？
- [ ] 并发/多线程场景是否考虑？

#### 3. 空值和未定义引用

- [ ] 可选参数是否检查？
- [ ] 字典/对象访问是否安全？
- [ ] 函数返回值是否验证？
- [ ] 变量使用前是否初始化？

#### 4. 并发安全

- [ ] 共享状态是否保护？
- [ ] 是否存在数据竞争？
- [ ] 锁的使用是否正确？
- [ ] 死锁风险是否存在？

#### 5. 安全问题

- [ ] 是否存在注入风险（SQL、命令、XSS）？
- [ ] 敏感数据是否保护？
- [ ] 权限检查是否充分？
- [ ] 输入验证是否完整？

#### 6. 资源管理

- [ ] 文件/连接是否正确关闭？
- [ ] 是否存在内存泄漏？
- [ ] 临时资源是否清理？
- [ ] 使用上下文管理器（with语句）？

#### 7. API 合约

- [ ] 接口参数是否验证？
- [ ] 返回值是否符合契约？
- [ ] 错误码/异常是否合理？
- [ ] 版本兼容性是否考虑？

#### 8. 缓存问题

- [ ] 数据更新时缓存是否失效？
- [ ] 缓存键是否包含所有相关参数？
- [ ] 缓存键计算是否一致？
- [ ] 缓存条件是否正确？
- [ ] 是否缓存了不应缓存的结果？
- [ ] 缓存穿透是否防护？
- [ ] 缓存更新策略是否合理？

#### 9. 代码规范

- [ ] 是否遵循项目编码规范？
- [ ] 命名是否一致？
- [ ] 是否符合架构模式？
- [ ] 是否有代码重复？

### 第四步：报告问题

**问题报告格式：**

```markdown
## 文件：path/to/file.py:行号

### 问题描述

简要描述问题

### 严重程度

- [ ] 严重（Critical）- 必须修复才能合并
- [ ] 重要（Major）- 强烈建议修复
- [ ] 一般（Minor）- 建议修复

### 具体问题

[类型：逻辑错误/边界条件/空值引用/并发问题/安全漏洞/资源管理/API违规/缓存问题/规范违反]

详细说明...

### 建议修复

```python
# 代码示例
```

### 影响

说明不修复的后果
```

**优先级排序：**

1. 严重 > 重要 > 一般
2. 按文件/模块分组
3. 每个文件内按行号排序

### 第五步：总结报告

**输出摘要：**

```markdown
# Diff Review 报告

## 概览

- 变更文件数：X
- 发现问题数：Y（严重：A，重要：B，一般：C）
- 主要关注领域：[列出]

## 问题分类

1. 逻辑错误：X 个
2. 边界条件：X 个
3. 缓存问题：X 个
...

## 必须修复项

列出所有严重级别问题

## 建议修复项

列出重要和一般级别问题
```

## 输出规范

### 报告格式

- 使用清晰的标题层级
- 每个问题包含：位置、类型、严重程度、描述、建议
- 代码示例使用语法高亮
- 提供可操作的建议

### 质量标准

- **准确性：** 只报告高置信度问题
- **可操作性：** 每个问题都有明确修复建议
- **完整性：** 覆盖所有 9 大审查类别
- **优先级：** 明确标识必须修复项

## 注意事项

1. **理解优于批评：** 先理解代码意图，再判断问题
2. **假设善意：** 假设作者有合理理由，询问而非指责
3. **关注问题：** 针对代码而非个人
4. **承认不确定性：** 不确定时明确说明，不要猜测
5. **提供建设性建议：** 不仅指出问题，还要提供解决方案
